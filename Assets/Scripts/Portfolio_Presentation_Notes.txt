[ 1. BOIDS 알고리즘 개요 ]
--------------------------------------------------------------------------------
- 창시자: Craig Reynolds (1986년)
- 목적: 자연스러운 군집 행동 시뮬레이션 (새, 물고기, 군중)
- 핵심 규칙 3가지:
  
  1) SEPARATION (분리)
     - 주변 이웃과 너무 가까워지지 않도록 회피
     - 가까울수록 더 강한 반발력
     - 공식: force += (내위치 - 이웃위치).normalized / 거리
  
  2) ALIGNMENT (정렬)
     - 주변 이웃들의 이동 방향에 맞춤
     - 이웃들의 평균 속도 계산
     - 공식: 평균속도 / 이웃수 - 내속도
  
  3) COHESION (응집)
     - 주변 이웃들의 중심점으로 이동
     - 무리 짓는 경향 생성
     - 공식: (무리중심 - 내위치).normalized


[ 2. GPU vs CPU 구현 비교 ]
--------------------------------------------------------------------------------
+------------------+---------------------------+---------------------------+
|                  | CPU (BoidController)      | GPU (GPUBoids)            |
+------------------+---------------------------+---------------------------+
| 최대 개체 수     | 50-200개                  | 16,000개 이상             |
| 복잡도           | 보이드당 O(n)             | O(n²) but 병렬화됨        |
| 물리 지원        | 가능 (Rigidbody)          | 불가능                    |
| 충돌 감지        | 가능 (OverlapSphere)      | 불가능                    |
| 사용 사례        | 상호작용 필요한 개체      | 시각적 군중/떼            |
+------------------+---------------------------+---------------------------+

GPU가 빠른 이유:
- CPU: 순차 처리 (한 번에 하나의 보이드)
- GPU: 병렬 처리 (수천 개의 보이드 동시 처리)
- 그룹당 256 스레드 × 여러 그룹 = 대규모 병렬 처리


[ 3. COMPUTE SHADER 작동 흐름 ]
--------------------------------------------------------------------------------
GPUBoids.cs가 매 프레임 두 개의 커널을 실행:

  프레임 시작
      │
      ▼
  ┌─────────────────────────────────────────────────────────┐
  │ PASS 1: ForceCS (힘 계산)                               │
  │ - 각 스레드가 하나의 보이드 담당                        │
  │ - 모든 다른 보이드를 읽어서 이웃 힘 계산                │
  │ - 결과를 _BoidForceBuffer에 기록                        │
  └─────────────────────────────────────────────────────────┘
      │
      ▼
  ┌─────────────────────────────────────────────────────────┐
  │ PASS 2: IntegrateCS (오일러 적분)                       │
  │ - _BoidForceBuffer에서 힘을 읽음                        │
  │ - 속도 갱신: vel += force * deltaTime                   │
  │ - 위치 갱신: pos += vel * deltaTime                     │
  │ - _BoidDataBuffer에 기록                                │
  └─────────────────────────────────────────────────────────┘
      │
      ▼
  프레임 끝

주요 파라미터:
- SIMULATION_BLOCK_SIZE = 256 (그룹당 스레드 수)
- 스레드 그룹 수 = Ceil(MaxObjectNum / 256)
- 예시: 16384 보이드 = 64개 스레드 그룹


[ 4. GPU 인스턴싱 렌더링 ]
--------------------------------------------------------------------------------
일반 렌더링:
  - 16000 보이드 = 16000 드로우콜 = 느림

GPU 인스턴싱 (DrawMeshInstancedIndirect):
  - 16000 보이드 = 1 드로우콜 = 빠름
  - 인스턴스별 데이터를 버텍스 셰이더에서 StructuredBuffer로 읽음

BoidsRender.cs → BoidsRender.shader 데이터 흐름:
  1. C#에서 버퍼 설정: Material.SetBuffer("_BoidDataBuffer", buffer)
  2. 셰이더에서 읽기: _BoidDataBuffer[unity_InstanceID]
  3. 버텍스 셰이더에서 인스턴스별 변환 행렬 생성
  4. 단일 드로우콜로 모든 인스턴스 렌더링

Indirect Arguments 버퍼 (uint 5개):
  args[0] = 인스턴스당 인덱스 수 (메시 삼각형 × 3)
  args[1] = 인스턴스 수 (보이드 개수)
  args[2] = 시작 인덱스 (보통 0)
  args[3] = 베이스 버텍스 (보통 0)
  args[4] = 시작 인스턴스 (보통 0)


[ 5. 셰이더 회전 수학 ]
--------------------------------------------------------------------------------
문제: 각 보이드를 속도 방향으로 회전시켜야 함

해결: 오일러 각도 → 회전 행렬 변환

  rotY = atan2(velocity.x, velocity.z)  // Heading (좌우 회전, Yaw)
  rotX = -asin(velocity.y / length)     // Pitch (상하 회전)

회전 순서: Ry × Rx × Rz (Heading-Bank-Attitude)

"+ 1e-8"을 나눗셈에 더하는 이유:
  - 속도 크기가 0일 때 0으로 나누기 방지
  - 1e-8 = 0.00000001 (엡실론 값)


[ 6. 메모리 관리 ]
--------------------------------------------------------------------------------
ComputeBuffer 생명주기:
  
  Start()     → new ComputeBuffer(...)   // GPU 메모리 할당
  OnDestroy() → buffer.Release()         // GPU 메모리 해제
  
주의: Release() 호출 안 하면 GPU 메모리 누수 발생!

BoidData 구조체 (24 바이트):
  - float3 Velocity (12 바이트)
  - float3 Position (12 바이트)
  - C#과 셰이더에서 동일하게 맞춰야 함

[ 8. 예상 면접 질문 ]
--------------------------------------------------------------------------------
Q: 왜 CPU 대신 Compute Shader를 사용했나요?
A: 병렬 처리 때문입니다. GPU는 수천 개의 보이드를 동시에 처리할 수 있지만,
   CPU는 순차적으로 처리합니다. 16K 보이드 기준 GPU가 100배 이상 빠릅니다.

Q: 시간 복잡도는 어떻게 되나요?
A: O(n²)입니다. 각 보이드가 모든 다른 보이드를 확인합니다. 
   하지만 GPU가 바깥 루프를 병렬화해서 n개 스레드로 실질적 O(n)입니다.

Q: 왜 Force와 Integrate 두 패스로 나눴나요?
A: 읽기/쓰기 충돌 방지입니다. 모든 보이드가 현재 위치를 읽은 후에
   쓰기가 일어나야 합니다. 패스를 분리해서 데이터 일관성을 보장합니다.

Q: GPU 인스턴싱이 어떻게 드로우콜을 줄이나요?
A: CPU가 오브젝트마다 변환 행렬을 보내는 대신, 셰이더가 GPU 버퍼에서
   인스턴스별 데이터를 직접 읽습니다. 한 번의 API 호출로 전부 렌더링합니다.

Q: StructuredBuffer를 사용하는 이유는?
A: 커스텀 구조체 데이터(위치 + 속도)를 셰이더에 전달할 수 있습니다.
   일반 버퍼는 기본 타입만 지원합니다.

Q: buffer.Release()를 안 하면 어떻게 되나요?
A: GPU 메모리 누수가 발생합니다. 앱 종료까지 메모리가 해제되지 않습니다.
   에디터에서는 플레이 세션마다 누적될 수 있습니다.

Q: CPU 버전은 Physics.OverlapSphere를 쓰는데 GPU 버전은 왜 안 쓰나요?
A: Unity Physics는 CPU에서 실행됩니다. Compute Shader는 PhysX에 
   접근할 수 없어서 GPU 버전은 브루트포스 거리 체크를 합니다.


[ 9. 적용된 최적화 기법 ]
--------------------------------------------------------------------------------
1. 공간 지역성 (Spatial Locality)
   - CPU 버전에서 반경 내 이웃만 체크 (모든 보이드 X)

2. 스레드 그룹 크기
   - 256은 대부분 GPU에 최적 (warp/wavefront 크기와 일치)

3. 프러스텀 컬링
   - 렌더링 바운드 설정으로 화면 밖 인스턴스 스킵

4. 더블 버퍼링
   - 읽기/쓰기 버퍼 분리로 레이스 컨디션 방지

5. Indirect 드로잉
   - Args 버퍼가 GPU에 있어서 인스턴스 수에 CPU-GPU 동기화 불필요
